# SECTION 1 — THE MOST IMPORTANT QUESTION FIRST

## Why Not Write Database Code in the Router?

This is the question every beginner skips. Day 54 answers it properly.

---

## Option A — SQLAlchemy Directly in the Router (WRONG)

```python
@app.post("/shorten")
def create_url(url: URLCreate, db: Session = Depends(get_db)):
    db_url = ShortenedURL(
        original_url=str(url.original_url),
        short_code="abc123"
    )
    db.add(db_url)
    db.commit()
    db.refresh(db_url)
    return db_url
```

**Works?** Yes. **Professional?** No. Here's why:

```
Every router function becomes a mixture of:
  → HTTP handling (request, response, status codes)
  → Business logic (generate short codes, validate rules)
  → Database operations (add, commit, refresh)

100 endpoints × 3 responsibilities each = 300 things to think about.

When you need to change how data is saved:
  Find every router that saves data.
  Edit all of them.
  Miss one. Bug introduced.

When you need to test the save logic:
  Must mock HTTP requests.
  Must mock Pydantic schemas.
  Must mock database.
  All three layers tested at once — can't isolate problems.

When you switch from PostgreSQL to Redis:
  Grep every router file.
  Edit all SQLAlchemy code.
  Hope you didn't miss any.
```

---

## Option B — Repository Pattern (CORRECT)

```
Client → Router → Service → Repository → Database

Router:     Receives HTTP. Validates with Pydantic. Returns responses.
Service:    Applies business rules. Generates short codes.
Repository: Saves, fetches, updates data. Talks to PostgreSQL.
Database:   Stores data permanently.
```

```
When you change how data is saved:
  Edit ONE file: url_repository.py
  Nothing else changes.

When you test the save logic:
  Run test_repository.py with just the Repository.
  No HTTP. No Pydantic. No service needed.

When you switch from PostgreSQL to Redis:
  Write redis_repository.py with same method signatures.
  Swap in one line.
  Everything else works identically.
```

---

## The Restaurant Analogy

```
Restaurant:  Customer → Waiter → Chef → Store Room
Our API:     Client → Router → Service → Repository → Database

Customer (Client):
  Doesn't know how the kitchen works.
  Just says: "I want a pizza."

Waiter (Router):
  Takes the order.
  Checks if the order makes sense (Pydantic validation).
  Returns the final dish (JSON response).
  NEVER goes into the store room.

Chef (Service):
  Decides HOW to make the pizza.
  Generates the short code.
  Applies business rules.
  Tells the store room: "I need flour and tomatoes."

Store Room (Repository):
  Provides ingredients when asked.
  Stores new items when told to.
  Knows NOTHING about what dish is being made.
  Just handles storage.
  NEVER decides what to cook.

Database (PostgreSQL):
  The physical storage.
  Rows, columns, indexes.
```

**The chef never walks into the store room. The service never queries the database directly. That's the pattern.**

# SECTION 4 — THE REPOSITORY FILE

## app/repositories/url_repository.py

```python
from sqlalchemy.orm import Session

from app.models.shortened_url import ShortenedURL


class URLRepository:
    """
    Handles all database operations for shortened URLs.

    Responsibilities:
      - Save new shortened URLs
      - Fetch URLs by short code
      - Increment click count
      - (Future) Update and delete operations

    Does NOT know about:
      - FastAPI or HTTP
      - Pydantic schemas or request validation
      - Business rules or short code generation
    """

    def create(self, db: Session, url: ShortenedURL) -> ShortenedURL:
        """
        Save a new shortened URL to the database.

        Args:
            db: SQLAlchemy database session
            url: ShortenedURL model object (not a Pydantic schema)

        Returns:
            The saved ShortenedURL with all database-generated values populated.
        """
        db.add(url)
        db.commit()
        db.refresh(url)
        return url
```

## Every Line Explained

### Import: `from sqlalchemy.orm import Session`

```python
from sqlalchemy.orm import Session

# Session is SQLAlchemy's type for database sessions.
# We use it as a type hint for the db parameter.

# Why type hint with Session?
#   → Pylance/PyCharm provides autocomplete for all session methods.
#     Type `db.` → see: add, commit, rollback, refresh, query, close...
#   → Makes the function signature self-documenting.
#     "This function needs a database session."
#   → Type checkers (mypy) can catch wrong arguments at check time.

# Why Session and not SessionLocal?
#   SessionLocal is the factory (creates sessions).
#   Session is the type (what a session IS).
#   Type hints use Session. Creating uses SessionLocal().
```

### Import: `from app.models.shortened_url import ShortenedURL`

```python
from app.models.shortened_url import ShortenedURL

# The Repository imports the SQLAlchemy MODEL.
# NOT the Pydantic schema (URLCreate, URLResponse).

# Why models, not schemas?
#
# The Repository's job: talk to the database.
# SQLAlchemy maps ShortenedURL to the shortened_urls table.
# Repository receives a ShortenedURL object and saves it.
# It has no reason to know about HTTP request bodies.
#
# If Repository received URLCreate (Pydantic):
#   Repository imports from schemas → depends on FastAPI world.
#   Switch to CLI: CLI has no Pydantic. Repository breaks.
#   Run tests: must create Pydantic objects just to test saving.
#
# If Repository receives ShortenedURL (SQLAlchemy model):
#   Repository only imports from models → database world only.
#   Switch to CLI: Service still creates ShortenedURL objects → Repository unchanged.
#   Run tests: create a ShortenedURL object directly → simple.
```

### Class: `class URLRepository`

```python
class URLRepository:

# Why a class instead of plain functions?
#
# Functions: url_repository_create(db, url) — works but hard to group.
# Class: URLRepository().create(db, url) — methods grouped by domain.
#
# Benefits of class-based repository:
#   → Namespace: all URL database operations live in URLRepository.
#   → Dependency injection: can inject the class, not individual functions.
#   → Testing: can subclass and override for testing.
#   → Future: add attributes (cache, logger) without breaking signatures.
#
# Alternative (Abstract class):
#   class BaseRepository(ABC):
#       @abstractmethod
#       def create(self, db, obj): pass
#   class URLRepository(BaseRepository):
#       def create(self, db, url): ...
#
# Version 1: simple class without ABC.
# In a larger codebase: abstract base class enforces interface contract.
```

### Method: `def create(self, db: Session, url: ShortenedURL) -> ShortenedURL`

```python
def create(self, db: Session, url: ShortenedURL) -> ShortenedURL:

# Parameters:
#   self   → Standard Python. Refers to the URLRepository instance.
#   db     → The active database session. Provided by Depends(get_db).
#   url    → The ShortenedURL object to save (pre-constructed by Service).

# Return type: -> ShortenedURL
#   Returns the SAME object but now populated with:
#     id         → auto-generated by PostgreSQL SERIAL
#     created_at → auto-generated by datetime.now(UTC) default
#     clicks     → 0 (from default=0)
#   All of these are populated AFTER db.refresh(url).

# Why return the saved object?
#   The caller (Service, and later Router) needs the complete object.
#   Specifically: id and created_at are needed in URLResponse.
#   Without returning it: caller has no way to access id.
```

### Three Database Lines — Complete Explanation

```python
db.add(url)
db.commit()
db.refresh(url)
```

**`db.add(url)` — Stage for Insertion:**

```
Before db.add(): SQLAlchemy session has no knowledge of url.
After db.add():  SQLAlchemy tracks url as a "pending insert".

The INSERT SQL has NOT been sent to PostgreSQL yet.
The object exists only in Python memory.
PostgreSQL has received nothing.

Analogy: You put a package on the conveyor belt.
It hasn't been processed yet — it's just waiting.
```

**`db.commit()` — Save Permanently:**

```
db.commit() does several things in sequence:
  1. SQLAlchemy generates the INSERT statement:
     INSERT INTO shortened_urls (original_url, short_code, clicks, created_at)
     VALUES ('https://google.com', 'abc123', 0, '2026-07-25T09:00:00+00:00')
     RETURNING id, created_at;  (or similar)

  2. psycopg2 sends this SQL to PostgreSQL over TCP.

  3. PostgreSQL executes it:
     - Generates id = 1 (SERIAL sequence)
     - Stores the row permanently on disk.
     - Releases any row-level locks.
     - Returns the generated id.

  4. The transaction is committed — now part of the permanent record.

After commit(): The row is in PostgreSQL. Cannot be un-done by rollback.
Without commit(): All changes exist only in the session's memory.
                 Rolling back or closing the session = all changes lost.
```

**`db.refresh(url)` — Sync Python Object with Database:**

```
After commit(), the Python object url is "stale":
  url.id         → Still None (we never set it)
  url.created_at → Still the value from the lambda default
  url.clicks     → 0 (we set this)

But PostgreSQL has:
  id = 1 (auto-assigned by SERIAL)
  created_at = actual timestamp when row was inserted

db.refresh(url) runs:
  SELECT * FROM shortened_urls WHERE id = 1;
  (or similar query using the primary key)

Now url in Python has:
  url.id         → 1  ✅
  url.created_at → datetime with actual PostgreSQL timestamp ✅
  url.clicks     → 0  ✅

Without refresh():
  url.id is None → when FastAPI tries to build URLResponse with id: None
  "ValidationError: id must be int, got None"
  Server error. Bad response to client.
```

**The Three Together:**

```
db.add(url)    → "I want to save this."
db.commit()    → "Save it now. Permanently."
db.refresh(url) → "Tell me what PostgreSQL generated."

Missing add(): Nothing happens. Object not tracked.
Missing commit(): Data never reaches PostgreSQL. Lost on session close.
Missing refresh(): Python object is stale. Missing id, created_at.
All three are required for the create pattern.
```

# SECTION 7 — KEY CONCEPTS (DAY 54 SUMMARY)

## The Repository Pattern

```
Separates database operations from business logic.

Flow: Client → Router → Service → Repository → Database

Repository knows:  SQLAlchemy models, database sessions
Repository does:   INSERT, SELECT, UPDATE, DELETE
Repository does NOT know: FastAPI, HTTP, Pydantic, business rules

Benefits:
  → Switch databases: only repository changes
  → Test in isolation: create model objects directly, no HTTP
  → Single responsibility: clear ownership of database code
```

## db.add() vs db.commit() vs db.refresh()

```
db.add(url)
  → Stages the object in the session (no SQL sent yet)
  → Object exists only in Python memory

db.commit()
  → Sends INSERT to PostgreSQL
  → Row is permanently stored
  → PostgreSQL generates: id (SERIAL), validates constraints

db.refresh(url)
  → Reloads the object from the database
  → Python object now has: id (PostgreSQL-generated), created_at (actual timestamp)
  → Without this: id is None → breaks URLResponse

All three required for the create pattern.
```

## Why Repository Receives SQLAlchemy Model, Not Pydantic Schema

```
Repository responsibility: database only.
Pydantic belongs to the API layer.

Repository receives ShortenedURL (SQLAlchemy):
  → Repository only imports from models/
  → No dependency on FastAPI or Pydantic
  → Reusable from any context (CLI, tests, scripts)

Repository receives URLCreate (Pydantic):
  → Repository imports from schemas/
  → Coupled to the API layer
  → Can't use Repository without Pydantic (breaks CLI, tests)
```

# SECTION 8 — INTERVIEW QUESTIONS

## Q1. What is the Repository Pattern?

The Repository Pattern separates database operations into a dedicated class. Instead of writing SQLAlchemy code in the router or service, all database interactions (create, read, update, delete) live in the Repository. The flow is: Client → Router → Service → Repository → Database. Each layer has one responsibility.

## Q2. What does `db.add()` do?

`db.add(obj)` stages the SQLAlchemy object in the current session as a pending INSERT. The SQL has NOT been sent to PostgreSQL yet. The object exists only in Python memory. It's like putting a package on a conveyor — it's waiting to be processed.

## Q3. What does `db.commit()` do?

`db.commit()` sends all pending changes in the session to PostgreSQL as a transaction. For an INSERT, PostgreSQL executes the query, assigns the SERIAL id, and stores the row permanently. After commit, the change is irreversible (can't rollback). Without commit, no data is ever saved.

## Q4. What does `db.refresh()` do?

`db.refresh(obj)` re-reads the object's data from the database. After a commit, PostgreSQL may have generated values (SERIAL id, server timestamps) that the Python object doesn't know about yet. `refresh()` syncs the Python object with the actual database state. Without it, `url.id` is still `None` — breaking any response that needs the id.

## Q5. Why should the Repository receive SQLAlchemy models instead of Pydantic schemas?

The Repository's responsibility is the database layer. It should only know about SQLAlchemy models and sessions. If it received Pydantic schemas, it would be coupled to the API layer — making it unusable from CLIs, test scripts, or batch jobs that don't use Pydantic. The Service acts as the bridge, converting Pydantic inputs into SQLAlchemy objects before passing them to the Repository.

## Q6. Why is test_repository.py only temporary?

It bypasses the Router and Service layers — it creates SQLAlchemy model objects directly and passes them to the Repository, skipping URL validation and short code generation. This is useful for isolated testing of the Repository in isolation, but in production all requests must go through the Router (for HTTP handling) and Service (for business logic). Once the Service and Router are built, the endpoint itself becomes the test.

## Q7. What is a Session in SQLAlchemy?

A Session represents one unit of work with the database — one "conversation". Operations (add, query, delete) within a session are tracked together. `commit()` saves them all as one transaction. `rollback()` cancels them all. The session is always closed when done to return the connection to the pool. In FastAPI, `get_db()` provides one session per request.

# SECTION 9 — LEETCODE #189: ROTATE ARRAY

## Problem

Given array `nums`, rotate it to the RIGHT by `k` steps. In-place modification required.

```
nums = [1,2,3,4,5,6,7], k = 3  →  [5,6,7,1,2,3,4]
nums = [-1,-100,3,99],   k = 2  →  [3,99,-1,-100]
```

---

## Understanding "Rotate Right"

```
"Rotate right by 1" = last element moves to front:
  [1,2,3,4,5] → [5,1,2,3,4]

"Rotate right by k" = last k elements move to front:
  k=3: [1,2,3,4,5,6,7] → [5,6,7,1,2,3,4]
       last 3: [5,6,7] move to front
       remaining: [1,2,3,4] go to back
```

---

## The Index Formula

```
Every element moves exactly k positions to the right.
New Index = (Old Index + k) % n

Example: nums = [1,2,3,4,5,6,7], k=3, n=7

Number  Old Index  New Index = (old+3)%7
  1        0         (0+3)%7 = 3
  2        1         (1+3)%7 = 4
  3        2         (2+3)%7 = 5
  4        3         (3+3)%7 = 6
  5        4         (4+3)%7 = 0   ← wraps!
  6        5         (5+3)%7 = 1
  7        6         (6+3)%7 = 2
```

---

## Critical Observation: k % n

```
nums = [1,2,3], k = 5

Rotate 3 times = back to original (full cycle).
Rotate 5 times = rotate 3 times + rotate 2 times = rotate 2 times.

5 % 3 = 2 → "effective rotation is 2"

Always compute: k = k % len(nums)
Otherwise: unnecessary work when k > n.
Edge case: if k is a multiple of n → k becomes 0 → no rotation needed.
```

---

## Approach 1 — Extra Array (Index Mapping) O(n) time, O(n) space

```python
class Solution(object):
    def rotate(self, nums, k):
        arr = [0] * len(nums)
        k = k % len(nums)

        for i in range(len(nums)):
            new_index = (i + k) % len(nums)
            arr[new_index] = nums[i]

        nums[:] = arr   # ← Must use nums[:] = arr, NOT nums = arr!
```

### Complete Dry Run

```
nums = [1,2,3,4,5,6,7], k=3

arr = [0,0,0,0,0,0,0]

i=0: new_index=(0+3)%7=3 → arr[3]=1 → [0,0,0,1,0,0,0]
i=1: new_index=(1+3)%7=4 → arr[4]=2 → [0,0,0,1,2,0,0]
i=2: new_index=(2+3)%7=5 → arr[5]=3 → [0,0,0,1,2,3,0]
i=3: new_index=(3+3)%7=6 → arr[6]=4 → [0,0,0,1,2,3,4]
i=4: new_index=(4+3)%7=0 → arr[0]=5 → [5,0,0,1,2,3,4]
i=5: new_index=(5+3)%7=1 → arr[1]=6 → [5,6,0,1,2,3,4]
i=6: new_index=(6+3)%7=2 → arr[2]=7 → [5,6,7,1,2,3,4]

nums[:] = arr → [5,6,7,1,2,3,4] ✅
```

### Critical Mistake: `nums = arr` vs `nums[:] = arr`

```python
# WRONG:
nums = arr
# This rebinds the LOCAL variable nums to point to arr.
# The original list passed by the caller is UNCHANGED.
# LeetCode's test still sees the original array. Fails.

# CORRECT:
nums[:] = arr
# This modifies the CONTENTS of the original list in-place.
# Every element is replaced with arr's elements.
# The original list object is modified. LeetCode sees the change. Passes.

# Python memory model:
# nums = arr    → nums now points to a NEW list (arr)
# nums[:] = arr → nums still points to the SAME list, but its contents change
```

## Approach 2 — Reverse Method O(n) time, O(1) space ✅ Optimal

### The Core Idea

```
The last k elements must go to the front.
Instead of moving them individually, use THREE reversal steps.

Original: [1, 2, 3, 4, | 5, 6, 7]
                          ↑ last k=3

Goal:     [5, 6, 7, | 1, 2, 3, 4]

Think of the array as two groups:
  Group A = [1,2,3,4]  (first n-k elements)
  Group B = [5,6,7]    (last k elements)

Goal: swap the groups AND preserve order within each.
```

### Three Reversal Steps

```
Step 1: Reverse the ENTIRE array
  [1,2,3,4,5,6,7] → [7,6,5,4,3,2,1]
  
  Notice: Group B's elements (5,6,7) are now at the front — but in REVERSE order (7,6,5).
  Group A's elements are at the back — but in REVERSE order (4,3,2,1).

Step 2: Reverse the FIRST k elements (fix Group B's order)
  [7,6,5 | 4,3,2,1] → [5,6,7 | 4,3,2,1]
  
  Group B is now correctly ordered at the front.

Step 3: Reverse the REMAINING elements (fix Group A's order)
  [5,6,7 | 4,3,2,1] → [5,6,7 | 1,2,3,4]
  
  Group A is now correctly ordered at the back.

Result: [5,6,7,1,2,3,4] ✅
```

### The Code

```python
class Solution(object):
    def rotate(self, nums, k):
        k = k % len(nums)          # Handle k > n

        nums.reverse()             # Step 1: reverse all
        nums[0:k] = nums[0:k][::-1]  # Step 2: reverse first k
        nums[k:] = nums[k:][::-1]    # Step 3: reverse rest
```

### Python Note on Slicing

```python
nums[0:k][::-1]
# Creates a temporary reversed slice.
# Assigns it back to nums[0:k].
# Internally: O(k) extra space for the temporary slice.
# Algorithmically: O(1) extra space (ignoring Python implementation details).
# In interviews: describe it as O(1) — the algorithm is O(1), even if Python uses temp memory.

# True O(1) implementation uses a helper function:
def reverse(nums, start, end):
    while start < end:
        nums[start], nums[end] = nums[end], nums[start]
        start += 1
        end -= 1

reverse(nums, 0, len(nums)-1)  # Step 1
reverse(nums, 0, k-1)          # Step 2
reverse(nums, k, len(nums)-1)  # Step 3
# This is genuine O(1) space — no temporary lists.
```

## Common Mistakes

```
Mistake 1: Forgetting k = k % len(nums)
  Without it: k=105 on a 100-element array → algorithm still works
  but does 5 extra full rotations unnecessarily.
  Or: confusing index calculations for large k.

Mistake 2: Using nums = arr instead of nums[:] = arr
  nums = arr: only the local variable changes. Original untouched.
  nums[:] = arr: modifies the actual list contents. Correct.

Mistake 3: Wrong reversal order
  MUST be: reverse all → reverse first k → reverse remaining.
  Any other order gives wrong result.

Mistake 4: Off-by-one in reverse helper
  reverse(nums, 0, k-1) not reverse(nums, 0, k)
  Indices are inclusive. k-1 is the last index of the first segment.

Mistake 5: Not handling k=0 or k=n
  k%n = 0: nothing to rotate. Code handles this correctly
  (all three reversals on a 0-length or n-length slice = no change).
```

## Why the Reverse Method Works — Intuition

```
Think of the array as two strings:
  A = "1234" (first n-k characters)
  B = "567"  (last k characters)

Original: A + B
Goal:     B + A

Reverse(A+B) = Reverse(B) + Reverse(A)
             = "765" + "4321"

Reverse the first k of that: Reverse(Reverse(B)) = B = "567"
Result so far: "567" + "4321"

Reverse the remaining n-k: Reverse(Reverse(A)) = A = "1234"
Final: "567" + "1234" = B + A ✅

The math of reversals: Reverse(Reverse(X)) = X.
Three reversals give us exactly the group swap we need.
```

## Pattern: Array Rotation / Modular Index Mapping

```
This problem introduces two patterns:

Pattern 1: Modular Index Mapping
  new_index = (old_index + k) % n
  Appears in: circular arrays, ring buffers, hash tables

Pattern 2: Reverse Method for Array Rotation
  Reverse all → Reverse first k → Reverse rest
  Appears in: #189 (this), string rotation, circular buffer rotation

The formula (i + k) % n appears whenever:
  → Elements need to "wrap around" the array
  → Circular data structures
  → Scheduling algorithms
  → Hash table probing
```

# SECTION 10 — IMPORTANT THINGS TO KNOW

```
 1. Repository Pattern: Router → Service → Repository → Database.
    Repository is the ONLY layer that writes SQLAlchemy code.

 2. db.add(obj): stages the object for INSERT. No SQL sent yet.
    db.commit(): sends INSERT to PostgreSQL. Row permanently saved.
    db.refresh(obj): reloads object from database to get generated values.
    All three are required for the create() pattern.

 3. Without db.commit(): data never reaches PostgreSQL.
    Session close without commit = all changes lost.

 4. Without db.refresh(): url.id is None after commit.
    PostgreSQL generated the id but Python object doesn't know yet.

 5. Repository receives SQLAlchemy Model (ShortenedURL), not Pydantic Schema.
    Repository should not depend on FastAPI/Pydantic. Database layer only.

 6. Service is the bridge: Pydantic → SQLAlchemy model → Repository.
    Service translates API layer data into database layer data.

 7. test_repository.py is a temporary isolated test.
    Build and test one layer before adding the next.
    Bottom-up testing: fewer bugs, easier to locate problems.

 8. nums[:] = arr (in-place modify contents) vs nums = arr (rebind variable).
    LeetCode requires in-place: always use nums[:] = arr.

 9. k = k % len(nums) before rotation.
    Rotating n times = same as original. Only k % n effective rotations.

10. Reverse Method for rotation: O(n) time, O(1) space.
    Three steps: reverse all → reverse first k → reverse rest.
    Classic interview pattern. Memorize the order.

11. new_index = (old_index + k) % n: the modular index formula.
    Handles wrap-around. Appears in circular array problems.

12. db.close() at the end of test_repository.py.
    Always close sessions to return connections to the pool.
    In FastAPI: get_db() handles this automatically via finally:.

13. The Repository does NOT generate short codes.
    Short code generation is business logic → belongs in Service.
    Repository only knows: "Save this model object."

14. class URLRepository: groups all URL database operations together.
    Makes the code organized, discoverable, and testable as a unit.

15. pgAdmin verification is the source of truth.
    "Did it save?" → Check pgAdmin. If the row appears, it works.
    Don't trust print statements alone for database correctness.
```
