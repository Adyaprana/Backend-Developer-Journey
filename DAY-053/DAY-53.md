# SECTION 1 — THE MOST IMPORTANT QUESTION

## Why Do We Need Pydantic Schemas When We Already Have SQLAlchemy Models?

This is the question every beginner asks. It deserves a complete answer.

---

## The Short Answer

```
SQLAlchemy Model  →  How data is STORED in PostgreSQL
Pydantic Schema   →  What data the CLIENT sends and receives
```

They serve completely different purposes. They must never be mixed.

---

## The Restaurant Analogy

```
You're in a restaurant.

Customer → Menu → Waiter → Kitchen → Waiter → Customer

THE MENU:
  Defines what the customer can ORDER.
  Doesn't contain recipes.
  Doesn't show how food is prepared.
  Shows only what customers are allowed to choose.

THE KITCHEN:
  Stores actual ingredients.
  Contains recipes.
  Prepares food based on orders.
  Customer NEVER enters the kitchen.

Now map this to our API:

Client → Schema (Menu) → FastAPI (Waiter) → Model (Kitchen) → Database (Ingredients)

PYDANTIC SCHEMA = THE MENU
  Defines what data the client can send or receive.
  Doesn't expose internal database fields.
  Doesn't show how data is stored.

SQLALCHEMY MODEL = THE KITCHEN
  Represents actual database tables and columns.
  Contains internal fields (id, clicks, created_at).
  Client NEVER sees the raw model.
```

---

## The Security Argument (Why This Matters)

Imagine we use the SQLAlchemy model directly as the API request body:

```python
# BAD — using the ORM model directly
@app.post("/shorten")
def create_url(url: ShortenedURL):   # ← SQLAlchemy model as request body
    ...
```

A malicious client could now send:

```json
{
    "id": 1,
    "original_url": "https://evil.com",
    "short_code": "admin",
    "clicks": 1000000,
    "created_at": "2020-01-01"
}
```

```
What happens:
  → They chose their own id (could overwrite existing records)
  → They set clicks to 1 million (fake analytics)
  → They chose short_code "admin" (potentially reserved path)
  → They set created_at in the past (fake timestamp)

All of this because we let the client send database-internal fields.
```

With Pydantic schemas:

```python
# GOOD — using schema as request body
@app.post("/shorten")
def create_url(url: URLCreate):   # ← Pydantic schema, only original_url allowed
    ...
```

Client can ONLY send:

```json
{
    "original_url": "https://google.com"
}
```

```
Server decides:
  id          → PostgreSQL SERIAL (auto)
  short_code  → generated by secrets.choice()
  clicks      → starts at 0
  created_at  → datetime.now(UTC)

Client controls: nothing except the URL to shorten.
This is correct. This is secure.
```

---

## SQLAlchemy vs Pydantic — The Technical Distinction

```
SQLAlchemy Model:                    Pydantic Schema:
─────────────────────────────        ────────────────────────────────
class ShortenedURL(Base)             class URLCreate(BaseModel)
Inherits from Base                   Inherits from BaseModel
Represents a DATABASE TABLE          Represents an API DATA SHAPE
Lives in models/                     Lives in schemas/
Used for: INSERT, SELECT, UPDATE     Used for: request validation, response
Knows about: columns, indexes,       Knows about: types, constraints,
             relationships, FK                    optional/required fields
Used BY: crud.py, repository layer   Used BY: FastAPI router endpoints
Not exposed to the internet          Directly faces the internet (input/output)
```

```
Server-generated: 4 fields
Total in database: 5 fields

```

---

## Why `HttpUrl` Instead of `str`?

This is one of the most powerful FastAPI features:

```python
original_url: str      # accepts ANYTHING
original_url: HttpUrl  # validates it's a real HTTP/HTTPS URL
```

**What `HttpUrl` validates:**

```
Accepted ✅:
  "https://google.com"
  "http://github.com/Adyaprana"
  "https://www.amazon.in/product?id=123"
  "https://subdomain.domain.co.uk/path/to/page"

Rejected ❌ (FastAPI auto-returns 422):
  "google"                   → no scheme (http/https)
  "not-a-url"                → not a URL
  12345                      → not a string
  "ftp://something.com"      → not http/https
  ""                         → empty string
  null                       → no value
```

**The validation is free:**

```python
# Without HttpUrl: you'd write this yourself
def validate_url(url: str):
    if not url.startswith("http://") and not url.startswith("https://"):
        raise ValueError("Must be a valid URL")
    if "." not in url:
        raise ValueError("Invalid URL format")
    # ... 20 more edge cases

# With HttpUrl: zero code needed
original_url: HttpUrl
# Pydantic handles RFC 3986 URL validation automatically.
# FastAPI returns 422 before your endpoint even starts.
```

**This is why FastAPI is loved over Flask** — Flask requires writing validation manually, FastAPI's type system handles it:

```
Client sends bad URL
        │
        ▼
Pydantic validates original_url: HttpUrl
        │
        ▼
Validation FAILS (not a valid URL)
        │
        ▼
FastAPI returns 422 Unprocessable Entity automatically
        │
        ▼
Your endpoint function is NEVER called
```

## `model_config = ConfigDict(from_attributes=True)` — Critical Setting

### The Problem Without It

```python
# In crud.py (future):
def create_url(db, url: URLCreate) -> ShortenedURL:
    db_url = ShortenedURL(
        original_url=str(url.original_url),
        short_code="aB92Kx",
        clicks=0
    )
    db.add(db_url)
    db.commit()
    db.refresh(db_url)
    return db_url   # ← returns a ShortenedURL OBJECT (not a dict)
```

```python
# In the endpoint (future):
@router.post("/shorten", response_model=URLResponse)
def shorten_url(url: URLCreate, db: Session = Depends(get_db)):
    result = create_url(db, url)   # ← result is a SQLAlchemy ShortenedURL object
    return result                  # ← FastAPI tries to convert to URLResponse
```

```
FastAPI gives result (ShortenedURL object) to Pydantic.
Pydantic tries: URLResponse(result)

WITHOUT from_attributes=True:
  Pydantic expects a DICT: {"id": 1, "original_url": "...", ...}
  But result is an OBJECT: ShortenedURL(id=1, original_url="...", ...)
  Pydantic cannot read object attributes.
  CRASH: ValidationError

WITH from_attributes=True:
  Pydantic reads: result.id, result.original_url, result.short_code
  Using Python's getattr() instead of dict["key"]
  Works perfectly.
  SQLAlchemy object → Pydantic model → JSON response
```

### Pydantic v1 vs v2 Syntax

```python
# PYDANTIC v1 (OLD — many tutorials still show this):
class URLResponse(BaseModel):

# PYDANTIC v2 (NEW — what we use):
class URLResponse(BaseModel):

# The syntax changed in Pydantic v2.

# Check version: pip show pydantic
```

# SECTION 9 — INTERVIEW QUESTIONS (SCHEMAS)

## Q1. What is the difference between a SQLAlchemy Model and a Pydantic Schema?

A SQLAlchemy Model defines how data is stored in the database — it maps a Python class to a table with columns, constraints, and relationships. A Pydantic Schema defines what data the API accepts and returns — it validates inputs, serializes outputs, and documents the API contract. They have completely different responsibilities and must never be the same class.

## Q2. Why don't we use the SQLAlchemy model directly as the API request body?

Because the database model contains server-managed fields that the client should never control: `id` (auto-generated by PostgreSQL), `short_code` (generated by our code), `clicks` (always starts at 0), `created_at` (server timestamp). Using the model directly would allow clients to send `{"clicks": 1000000}` or `{"id": 1}`, overwriting server-generated values. Schemas expose only client-controllable fields.

## Q3. Why use `HttpUrl` instead of `str`?

`str` accepts any string, including "hello", "12345", or "not-a-url". `HttpUrl` is a Pydantic type that validates the value is a properly formatted HTTP or HTTPS URL according to RFC 3986. Invalid inputs are automatically rejected with HTTP 422 before the endpoint function even runs. No validation code needs to be written.

## Q4. What does `model_config = ConfigDict(from_attributes=True)` do?

By default, Pydantic reads data from dictionaries. But crud functions return SQLAlchemy model objects (not dicts). `from_attributes=True` tells Pydantic to read data by accessing object attributes (`obj.id`, `obj.name`) instead of dictionary keys (`dict["id"]`). This allows SQLAlchemy objects to be automatically converted to Pydantic response models and serialized as JSON.

## Q5. Why have three separate schemas (URLCreate, URLResponse, URLStats)?

Each schema serves a different endpoint with different data needs. `URLCreate` contains only what the client sends (one field). `URLResponse` contains what the client receives after shortening (id, original_url, short_code, short_url). `URLStats` contains analytics (original_url, short_code, clicks, created_at). Separate schemas make the API safer, clearer, and easier to maintain. Combining them would either expose too much data or accept too much from the client.

## Q6. Why is `short_url` in URLResponse but not stored in the database?

`short_url` is a derived value: `BASE_URL + "/" + short_code`. It can always be reconstructed from stored data. Storing it in the database would introduce redundancy — if the domain ever changes, every row would need updating. We construct it in the service/crud layer when building the response, keeping the database normalized.

# SECTION 10 — LEETCODE #88: MERGE SORTED ARRAY

## Problem

Given two sorted arrays `nums1` and `nums2`, merge `nums2` into `nums1` in-place so the result is sorted.

- `nums1` has length `m + n`. First `m` elements are valid. Last `n` are placeholders (zeros).
- `nums2` has `n` valid elements.

```
nums1 = [1,2,3,0,0,0], m = 3
nums2 = [2,5,6],        n = 3

Output: [1,2,2,3,5,6]
```

---

## The Critical Understanding — Zeros Are NOT Data

```
nums1 = [1, 2, 3, 0, 0, 0]
                 ↑  ↑  ↑
         These are EMPTY SPACES, not real values.

Better visualization:
nums1 = [1, 2, 3, _, _, _]
         ← valid →  ← empty →
         (m=3)       (n=3)

nums2 = [2, 5, 6]
        ← all valid →
        (n=3)
```

---

## Why Appending Then Sorting is Not Optimal

```python
# Approach 1: Append + Sort
def merge_brute(nums1, m, nums2, n):
    k = 0
    for i in range(len(nums1)):
        if i >= m:
            nums1[i] = nums2[k]
            k += 1
    nums1.sort()
    return nums1

# Time: O((m+n) log(m+n)) — sorting wastes the "already sorted" property

# Problem:
# Both arrays are ALREADY SORTED.
# Sorting again ignores that advantage.
# Interviewers expect us to USE the sorted property for O(m+n).
```

---

## Why Merging From The Front Fails

```
nums1 = [1, 2, 3, _, _, _]
nums2 = [2, 5, 6]

Start from front. Compare 1 and 2.
1 < 2. Keep 1 in place.

Now compare 2 and 2. Equal. Place nums2's 2.
nums1[1] = 2    ← overwrites the original 2!
The original nums1[2]=3 is still there.
But we just lost nums1[1]=2 permanently.

As we proceed, we overwrite elements before using them.
Data is permanently destroyed.
This is why merging from the front is impossible in-place.
```

---

## The Big Insight: Fill From the Back

```
The back of nums1 has EMPTY SPACES.
Nothing important is there.
Writing to the back overwrites nothing meaningful.

Strategy:
  Look at the LARGEST elements of both arrays.
  Place the bigger one at the LAST empty position.
  Move that pointer inward.
  Repeat.

Example:
  nums1 = [1, 2, 3, _, _, _]
  nums2 = [2, 5, 6]

  Largest in nums1: 3
  Largest in nums2: 6

  6 > 3 → place 6 at last position
  nums1 = [1, 2, 3, _, _, 6]   ← safe, last was empty
  p2 moves left (p2 used)

  Next compare: 3 vs 5
  5 > 3 → place 5
  nums1 = [1, 2, 3, _, 5, 6]

  Next compare: 3 vs 2
  3 > 2 → place 3
  nums1 = [1, 2, 3, 3, 5, 6]   ← 3 copies to p1's slot, moves p1

  ...eventually: nums1 = [1, 2, 2, 3, 5, 6] ✅
```

---

## Approach 1 — Append + Sort (Simple but Not Optimal)

```python
class Solution(object):
    def merge(self, nums1, m, nums2, n):
        k = 0
        for i in range(len(nums1)):
            if i >= m:
                nums1[i] = nums2[k]    # fill empty slots with nums2
                k += 1
        nums1.sort()                   # sort the combined array
        return nums1

# Works. Not optimal. O((m+n) log(m+n)) time.
```

---

## Approach 2 — Three Pointers, Merge From The End ✅ Submitted (Optimal)

```python
class Solution(object):
    def merge(self, nums1, m, nums2, n):
        p1 = m - 1         # last valid index in nums1
        p2 = n - 1         # last valid index in nums2
        write = m + n - 1  # last position in nums1 (where to write)

        while p2 >= 0:                           # while nums2 has elements left
            if p1 >= 0 and nums1[p1] > nums2[p2]:
                nums1[write] = nums1[p1]          # nums1's element wins
                p1 -= 1                           # move p1 left
            else:
                nums1[write] = nums2[p2]          # nums2's element wins
                p2 -= 1                           # move p2 left
            write -= 1                            # always move write left

        return nums1
```

---

## The Three Pointers Explained

```
p1 = m - 1       → points to the last VALID element of nums1
                   Example: m=3, p1=2 → nums1[2]=3

p2 = n - 1       → points to the last element of nums2
                   Example: n=3, p2=2 → nums2[2]=6

write = m + n - 1 → points to the last position of nums1
                    Example: m=3, n=3, write=5 → nums1[5]=0 (empty)

Three responsibilities:
  p1    → current largest candidate from nums1
  p2    → current largest candidate from nums2
  write → where the overall largest goes
```

---

## The `while p2 >= 0` Loop — Why This Condition?

```python
while p2 >= 0:

# We stop when nums2 is exhausted.
# Why not also check p1?

# Case 1: nums2 runs out first.
# p2 < 0 → loop stops.
# Remaining nums1 elements are ALREADY in their correct positions.
# No action needed. They were sorted to begin with.

# Case 2: nums1 runs out first (p1 < 0).
# The condition p1 >= 0 in the if-block handles this.
# When p1 < 0: condition is False → always take from nums2.
# Remaining nums2 elements copy into the front of nums1.

# Key insight: nums1's elements that haven't been touched
# are already in the right place (they're smaller than everything written so far).
```

---

## The `if p1 >= 0` Guard

```python
if p1 >= 0 and nums1[p1] > nums2[p2]:

# p1 >= 0 checks: Does nums1 still have valid elements?
# If p1 = -1: nums1 is exhausted. Only nums2 elements remain.
# Without this guard: nums1[-1] = last element (Python wraps around).
# This would access an invalid position and corrupt the merge.

# Edge case this handles:
# nums1 = [0], m = 0, nums2 = [1], n = 1
# p1 = -1 immediately. p2 = 0.
# if p1 >= 0 → False → take from nums2.
# nums1[0] = nums2[0] = 1
# Result: [1] ✅
```

---

## The `else` Branch — Why It Catches Everything

```python
else:
    nums1[write] = nums2[p2]
    p2 -= 1

# The else handles THREE cases:
#
# Case 1: nums1 is exhausted (p1 < 0)
#   → Take from nums2
#
# Case 2: nums2's element is GREATER than nums1's
#   → Take from nums2
#
# Case 3: Both elements are EQUAL
#   → Take from nums2 (either is fine for equal values)

# Why take from nums2 (not nums1) when equal?
# In theory: either is correct — both values are the same.
# In practice: taking from nums2 simplifies the loop.
# p2 decrements → eventually p2 < 0 → loop stops.
# If we took from nums1 when equal: we'd need extra logic.
```

## Common Mistakes

```
Mistake 1: Merging from the front
  Overwrites valid data before it's been used.
  Impossible to fix without extra space.

Mistake 2: Only one loop condition (while p1 >= 0 or p2 >= 0)
  Not needed. When p2 < 0: stop. nums1's remaining elements
  are already in the correct positions.

Mistake 3: Missing p1 >= 0 guard
  When nums1 is exhausted (p1 = -1):
  nums1[p1] = nums1[-1] (Python wraps to last element)
  Corrupts the array.

Mistake 4: Moving wrong pointer
  "Winner moves. Loser waits."
  The element we just placed is used. Its pointer moves.
  The other element is still needed. Its pointer stays.

Mistake 5: Forgetting to move write
  write must decrement EVERY iteration.
  Every iteration fills exactly one position.
```

---

## The Pattern — Merge from End / Three Pointers

```
This pattern appears when:
  Two sorted arrays must be merged in-place
  One array has extra space at the end

Template:
  p1 = end of valid elements in array1
  p2 = end of valid elements in array2
  write = end of total space in array1

  while p2 >= 0:
      if p1 >= 0 and array1[p1] > array2[p2]:
          array1[write] = array1[p1]
          p1 -= 1
      else:
          array1[write] = array2[p2]
          p2 -= 1
      write -= 1
```

# SECTION 11 — IMPORTANT THINGS TO KNOW

```
 1. SQLAlchemy Model = database table. Pydantic Schema = API contract.
    Never use one in place of the other.

 2. URLCreate contains only original_url — one field.
    The server generates everything else.

 3. HttpUrl validates the value is a real HTTP/HTTPS URL.
    Pydantic rejects invalid URLs before your endpoint runs.

 4. model_config = ConfigDict(from_attributes=True) allows Pydantic
    to read SQLAlchemy object attributes instead of dict keys.

 5. Pydantic v1 used orm_mode=True. Pydantic v2 uses from_attributes=True.
    Always check your Pydantic version when reading tutorials.

 6. URLResponse has short_url — a derived field constructed in the service layer.
    short_url is NOT stored in the database (domain + "/" + short_code).

 7. URLStats includes clicks and created_at — analytics fields.
    URLResponse does not include them — they're irrelevant at creation time.

 8. Three separate schemas for three separate concerns.
    Never merge them — each serves a different purpose.

 9. Merge Sorted Array: always fill from the back, not the front.
    The back of nums1 has empty space. The front has valid data.

10. Three pointers: p1 (last valid nums1), p2 (last nums2), write (last position).
    Winner moves. Write always moves.

11. while p2 >= 0 is sufficient. When p2 < 0, nums2 is done.
    Remaining nums1 elements are already in correct positions.

12. p1 >= 0 guard prevents accessing nums1[-1] after nums1 is exhausted.
    Without it: Python wraps to last element → corrupt merge.

13. When elements are equal: take from nums2 (simpler logic, same result).

14. Merge from End pattern: two sorted arrays + extra space at end.
    Compare from back, place larger at write, advance winner and write.

15. HttpUrl in Pydantic is validated before the endpoint function runs.
    This is FastAPI's automatic validation — no try/except in your code.
```
